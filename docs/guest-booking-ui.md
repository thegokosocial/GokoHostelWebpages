# Guest booking browsing, checkout, and private lookup

## Scope and rollout

The homepage hero and `/book` share the **Find a stay / My booking** panel. When `nativeCheckoutReady` is true (migrations **0059–0062**, hold/guest env flags, destination `/book`, Razorpay credentials for the selected `gatewayEnvironment`), Review offers advance/full/pay-at-property and creates a provisional PMS booking via `POST /api/guest-booking/checkout`. Confirmation lives at `/booking/[reference]` with `guestAccessToken` in **sessionStorage** only. Flip Test ↔ Live in Booking Settings. Preview (`/book/preview`) still blocks payment writes.

## Search and selection workflow

1. Choose check-in/check-out only. No guest-count or bed-count input. Beds are chosen after Check availability. The strict query rejects `guests` and `units`. No children; the 18–35 rule remains. Arrival is today through 365 days ahead in IST; checkout later, maximum 30 occupied nights.
2. GET `/api/guest-booking/availability` validates a strict query and rejects duplicate keys. It is cloud-only, read-only and `no-store`.
3. Existing PMS range-picker allocations, blocks and OTA reservations determine online availability. The server uses nondeleted physical beds/dorms and excludes any overlapping unexpired `held` native inventory holds, using database time. Double beds require both physical slots. An absent internal holds table is permitted for advisory browsing because public hold creation is still disabled; an existing broken table or invalid hold data fails the search rather than being ignored.
4. Room cards group by dorm and sellable-unit type. No physical bed IDs, guest names, contact details, API credentials or owner tokens are returned.
5. Prices come from active existing Channel Manager room/rate-plan mappings and daily rates. Exactly one active room mapping per dorm is required. Each occupied night must have a positive safe whole-rupee rate; a departure-day row is also required to evaluate departure restrictions. Occupancy prices use adult1/adult2 when configured, otherwise the unit base rate. A mixed bunk/double dorm requires explicit adult2 prices for doubles; it cannot guess the single-bed tariff. Stop-sell, minimum/maximum stay, closed arrival/departure and advance-booking bounds are checked. Each eligible active rate plan is offered independently, not arbitrarily selected as the cheapest.
6. Cards show nightly breakdown and entire-stay price **per unit before taxes**. The selection/review summary adds estimated tax from the existing `booking_tax_rate` PMS setting, rounds once to whole rupees using the shared calculator, honors explicit 0%, and uses the existing 5% default only when the setting is absent. Corrupt/out-of-range saved tax fails search rather than guessing. These are estimates, not immutable accepted quotes. Missing/ambiguous/ineligible tariffs show an explanation and disable quantity selection; zero prices and fabricated rate fallbacks are not advertised.
7. Listings appear only after Search. Main price is per bed/night (From the minimum occupied-night tariff when nights vary); the separate per-bed entire-stay subtotal and nightly breakdown remain visible. One rate plan applies to each category's quantity; switching reprices without adding beds. Plus/minus rechecks stock and the combined bed-count limit on every tap, not guest capacity. Whole doubles count as one bed and are charged at their whole-double tariff. Review requires at least one priced bed and no stock/limit violation. Reaching the limit disables all Add controls and instructs removal before adding. Changing dates clears results; changing plan/quantity closes review. Representative marketing photos and unknown-category placeholders remain; no fabricated discounts or confirmation claims.
8. Review shows dates, selected beds/plans, sleeping capacity, subtotal, tax and total. When checkout is ready, guest name/email are required and posted to prepare checkout; payment choice radios follow Booking Settings. Only `guestAccessToken` is stored in sessionStorage after prepare (never `ownerToken`). Hold countdown uses `holdExpiresAt` from the server. Double-submit reuse keeps a stable `requestKey`; Razorpay Checkout is opened with `retry.enabled: false`.
9. **Pay now** / **Confirm reservation** call checkout → optional Razorpay Standard Checkout (all methods) → verify → `/booking/[reference]`. If readiness is false, payment stays disabled and WhatsApp enquiry remains available. Physical hold limit is **4 bed IDs** (selecting 3 doubles = 6 beds is rejected even when unit count ≤ `maxSelectedBeds`).

## Private existing-booking workflow

1. My booking takes a confirmation reference plus the booking email. POST `/api/guest-booking/lookup` action `request` searches nondeleted PMS bookings by Goko/external reference and email, case-insensitively. Missing and duplicate matches disclose nothing.
2. Every request returns a fresh opaque challenge ID and the same generic message. A matched booking atomically claims one code per booking/email per ten minutes, including across reference aliases. Throttled retries do not return the previous challenge ID (which would be an enumeration signal). Keep the original page open; repeated requests may return an unusable opaque challenge until the cooldown expires.
3. Six-digit cryptographic codes are emailed from **booking@gokohostel.com**, through the existing Cloudflare `EMAIL` binding, to the stored booking address. Only a salted/secret-bound hash is stored. No plaintext code or contact address is stored in the challenge table. Ambiguous delivery retains the cooldown and produces a sanitized operational warning, not an existence-revealing guest error.
4. `verify` accepts only a UUID challenge and six digits, using POST bodies, never URL parameters/storage. The database atomically counts attempts (maximum five) and expiry; successful codes are consumed once. Concurrent verification can disclose details only to one successful request.
5. Details are a minimized current booking snapshot: reference, guest name, dates, room type, guest count, booking/payment status and INR total/paid/refunded. No contact data, raw OTA payload, identity documents, bed IDs or gateway identifiers are returned. This read-only view cannot authorize refunds, cancellation or payment.
6. Cross-origin browser requests are rejected; body streaming is limited to 4 KiB. Responses are sanitized, `no-store`, and `no-referrer`. Pi returns 403 before reading storage or sending email.

Activation requires migration **0061_guest_booking_lookup.sql**, an independently provisioned **GUEST_BOOKING_LOOKUP_SECRET** of at least 32 characters, and a working verified sender/EMAIL binding. Absence fails closed with a helpful contact option. Do not put the secret into a public environment variable, CMS or source control. No live migration or secret change is performed by this code change.

Before public lookup activation, configure edge/IP request limits and verify delivered messages, origin handling on the deployed canonical hostname, database races and expiry on deployed D1. The per-booking cooldown/attempt limit is not a replacement for edge abuse controls or a formal resistance-to-timing-enumeration review. Schedule expiry cleanup for this ephemeral table; do not sync it to Pi.

## Safe visual preview

For local review, use `GOKO_BOOKING_UI_PREVIEW=true` and `/book/preview`; otherwise 404, with noindex metadata. Dates start one week ahead but are editable and never reset on search. Search now uses the same read-only `/api/guest-booking/availability` fetch as `/book`: actual connected Inventory nightly tariffs, current stock, configured tax and saved bed limit. All hardcoded room/rate/stock/tax/limit fixtures have been removed. Lookup emails and reservation/payment creation remain disabled in preview. Missing database bindings, broken mappings, rates or settings produce unavailable/error states, never fabricated prices. A standalone `next start` without a working Cloudflare database context may therefore show unavailable; this code does not provision bindings, copy production data or proxy to production. Keep the local preview flag off in production.
