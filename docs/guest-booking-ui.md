# Guest booking browsing, checkout, and private lookup

## Scope and rollout

The homepage hero and `/book` share the **Find a stay / Find my booking** panel. The homepage hero no longer shows Book now / Explore rooms CTAs above the panel (header Book remains). When `nativeCheckoutReady` is true (migrations **0059–0062**, hold/guest env flags, destination `/book`, Razorpay credentials for the selected `gatewayEnvironment`), Review offers advance/full/pay-at-property and creates a provisional PMS booking via `POST /api/guest-booking/checkout`. Confirmation lives at `/booking/[reference]` with `guestAccessToken` in **sessionStorage** only. Flip Test ↔ Live in Booking Settings. Preview (`/book/preview`) still blocks payment writes.

## Search and selection workflow

1. Choose check-in/check-out only. No bed-count input at search. On the homepage, **Check availability** redirects to `/book?checkinDate=&checkoutDate=` and `/book` auto-runs the same availability search so results continue there. On `/book` itself, Check availability searches in place. Beds are chosen after results; party size (**Guests**) is collected on Review. The strict query rejects `guests` and `units`. No children; the 18–35 rule remains. Arrival is today through 365 days ahead in IST; checkout later, maximum 30 occupied nights.
2. GET `/api/guest-booking/availability` validates a strict query and rejects duplicate keys. It is cloud-only, read-only and `no-store`.
3. Existing PMS range-picker allocations, blocks and OTA reservations determine online availability. The server uses nondeleted physical beds/dorms and excludes any overlapping unexpired `held` native inventory holds, using database time. Double beds require both physical slots. An absent internal holds table is permitted for advisory browsing because public hold creation is still disabled; an existing broken table or invalid hold data fails the search rather than being ignored.
4. Room cards group by dorm and sellable-unit type. No physical bed IDs, guest names, contact details, API credentials or owner tokens are returned.
5. Prices come from active existing Channel Manager room/rate-plan mappings and daily rates. Exactly one active room mapping per dorm is required. Each occupied night must have a positive safe whole-rupee rate; a departure-day row is also required to evaluate departure restrictions. Occupancy prices use adult1/adult2 when configured, otherwise the unit base rate. A mixed bunk/double dorm requires explicit adult2 prices for doubles; it cannot guess the single-bed tariff. Stop-sell, minimum/maximum stay, closed arrival/departure and advance-booking bounds are checked. Each eligible active rate plan is offered independently, not arbitrarily selected as the cheapest.
6. Cards show nightly breakdown and entire-stay price **per unit before taxes**. The selection/review summary adds estimated tax from `booking_tax_rate` when Channel Manager **Apply tax rate for Online Goko website booking** is on (`booking_tax_apply_website`, default on); otherwise tax is 0%. Rounds once to whole rupees using the shared calculator, honors explicit 0%, and uses the existing 5% default only when the rate setting is absent and apply is on. Corrupt/out-of-range saved tax fails search rather than guessing. These are estimates, not immutable accepted quotes. Missing/ambiguous/ineligible tariffs show an explanation and disable quantity selection; zero prices and fabricated rate fallbacks are not advertised.
7. Listings appear only after Search. When availability is returned, the page gently scrolls the first available dorm-bed card into view with header-safe spacing; reduced-motion users receive an immediate scroll. Empty results remain near the search controls so the no-availability message is visible. Main price is per bed/night (From the minimum occupied-night tariff when nights vary); the separate per-bed entire-stay subtotal and nightly breakdown remain visible. One rate plan applies to each category's quantity; switching reprices without adding beds. Plus/minus rechecks stock and the combined bed-count limit on every tap, not guest capacity. Whole doubles count as one bed and are charged at their whole-double tariff. Review requires at least one priced bed and no stock/limit violation. Reaching the limit disables all Add controls and instructs removal before adding. Changing dates clears results; changing plan/quantity closes review. Guest-facing names, descriptions, amenities, room photos, and washroom photos come from Booking Settings, with the legacy room catalog only as an unsaved fallback. A configured direct-booking discount shows the standard Inventory/OTA-comparison price, direct price, and savings; no fabricated discount or confirmation claim is shown.
8. Review shows dates, selected beds/plans, sleeping capacity (“Sleeps up to N”), subtotal, tax and total. When Booking Settings **Direct booking discount** is greater than 0% and rates expose `standardSubtotalRupees` above the discounted subtotal, the sticky estimate and Review show a strikethrough compare-at price above the bold paid amount (per line, bed subtotal, and estimated total including tax). Tax line stays a single figure on the discounted base; the sticky footer still appends “You save …” on the bed subtotal difference. At 0% discount, only the paid price shows (no strike). When checkout is ready, guest name, email, phone and **Guests** (party size, default 1) are required (marked *) and posted to prepare checkout; Pay now stays disabled until contacts are filled and `1 ≤ persons ≤ capacity`. If Guests exceeds capacity, Review shows: “Your selection sleeps up to N. Add beds for M more guest(s).” (same wording from `prepareGuestCheckout` on the server). Server re-checks capacity after allocate and stores `bookings.persons` as the guest-entered count (not capacity). No live/test payment disclaimer under Pay now. Payment choice radios follow Booking Settings. Only `guestAccessToken` is stored in sessionStorage after prepare (never `ownerToken`). Hold countdown uses `holdExpiresAt` from the server; when the hold hits zero, Review replaces Pay with **Recheck availability** (clears hold/request key and re-searches the same dates). If readiness is false, Review shows **Recheck payment readiness** (re-fetches `/api/booking/config`) plus WhatsApp enquiry. Each Pay attempt mints a **new** `requestKey` (after fail/soft cancel, Try again does too) so cancelled recovers cannot open a false confirmation. Razorpay script preloads on Review for advance/full; claim runs in parallel with script load. WhatsApp CTAs are not shown on the ready Review pay path (footer Contact Goko remains).
9. **Pay now** / **Confirm reservation** show a full-screen wait overlay (`CheckoutWaitOverlay`: securing beds / confirming reservation for pay-at-property → payment window → confirming → confirmation redirect) with “do not press Back” messaging and scroll lock. Success path calls `disarmCheckoutLeaveGuard()` then `location.replace` so beforeunload does not flash Leave site. **Definite fail** (`payment.failed`) / unpaid dismiss → abandon, failure/cancelled panel + **Try again**. **Unclear** (verify timeout/network after Razorpay handler, missing razorpay when `requiresPayment`) → `uncertain: true` abandon (not the pagehide beacon), support copy + WhatsApp, no auto-retry pay. Tab close mid-Razorpay still uses pagehide **abandon** (may fulfil if already captured). Aiosell push and confirmation email (Booking Settings → **Email Templates** confirmation subject/body) run after beds are confirmed (`waitUntil`). Redirect only when `state === "fulfilled"` or `bookingStatus === "received"`. If readiness is false, payment stays disabled until readiness returns. Physical hold limit is **4 bed IDs** (selecting 3 doubles = 6 beds is rejected even when unit count ≤ `maxSelectedBeds`).
10. **Change stay:** guest confirmation explains that changes, modifications, or cancellations should use **Copy booking details** plus the in-card **WhatsApp** button (prefilled message). The site-wide floating WhatsApp control is hidden on `/booking/[reference]`. Self-serve amend UI is retired (`POST /api/guest-booking/amend` → 403). Staff change website stays via Admin **Edit Booking** (same as walk-in; dates + persons + beds in one save); stay-shape edits **reprice** Total / Due from nightly × nights × beds (Paid unchanged). Guest confirmation shows an **Updated** badge when history has a stay-shape reservation edit, and Payment/rooms come from the live booking row (not the original quote). **Cancel booking** remains a full button when `canCancel`. Staff with `canDeleteBooking` can hard-delete **unpaid** website bookings (paid ones must cancel/refund first) and **Refund orphan capture** on cancelled website stays that still show Razorpay capture (`refundWebsiteOrphan`).

## Mobile-first interface

Booking Settings → Booking & Policies exposes **Maximum beds per website selection**, integer 1–100, default 4 for absent/older valid JSON. Booking Settings → Rooms & Rates exposes a global **Direct booking discount**, integer 0–80%, default 0. The server applies it to every occupied-night Inventory tariff before tax, rounds each discounted nightly unit price to whole rupees, and preserves the standard subtotal/savings in accepted quotes and checkout snapshots. Existing admin saves validate and revision-protect both values. Corrupt settings fail closed. Guests select up to stock and combined bed count; Review **Guests** is the actual party size and must stay within sleeping capacity. Preview fetches the saved settings with no fixture override. Prepare/amend checkout re-read and enforce the latest values server-side. Rate arithmetic is bounded for 100 beds × 30 nights × 100% maximum tax.

Rate-source review: the earlier screenshot used synthetic 850/950 fixture prices; those fixtures are now removed. Both `/book` and preview read active mappings and Inventory `daily_rates`, using adult1/base for singles and explicit adult2 on occupied nights for mixed-dorm doubles. Checkout still needs a departure-restriction row, not a double tariff, because it is not charged. Local tests do not certify actual merchant tariff values.

## Private existing-booking workflow

1. **Find my booking** takes a confirmation reference plus the booking email. The tab notes that lookup currently supports bookings made through the Goko website only. POST `/api/guest-booking/lookup` action `request` searches nondeleted PMS bookings by Goko/external reference and email, case-insensitively. Missing and duplicate matches disclose nothing.
2. **OTP gate** is Admin setting `requireLookupOtp` (default **true**), exposed on `/api/booking/config` and availability `paymentOptions`. When **on**: every request returns a fresh opaque challenge ID and the same generic message; a matched booking atomically claims one code per booking/email per ten minutes. When **off**: a unique match returns the booking (and manage token if applicable) immediately; mismatches return a generic miss message with no challenge and no booking blob.
3. When OTP is on: six-digit codes are emailed from **booking@gokohostel.com**. Only a salted/secret-bound hash is stored. `verify` accepts UUID challenge + six digits; max five attempts; codes consumed once.
4. After successful verify (or direct fetch when OTP off):
   - **Website booking** (checkout row): mint `guestAccessToken`, store hash, return `{ booking, guestAccessToken, manageUrl }`. **Find my booking** stores sessionStorage and redirects to `/booking/[reference]`.
   - **Non-website / no checkout:** minimized booking snapshot only — no token.
5. `/booking/[reference]` renders `GuestBookingManage` (status, rooms, payment, due). Changes go through copy-details + in-card WhatsApp (site float hidden on this route); Cancel is a full button when `canCancel`. `canModify` is always false in the public snapshot.
6. Cross-origin rejected; 4 KiB body limit; Pi 403.

Activation requires migration **0061**, `GUEST_BOOKING_LOOKUP_SECRET` (≥32 chars), and EMAIL binding. Turning off OTP weakens proof to reference+email only — document for ops.

## Safe visual preview

For local review, use `GOKO_BOOKING_UI_PREVIEW=true` and `/book/preview`; otherwise 404, with noindex metadata. Dates start one week ahead but are editable and never reset on search. Search now uses the same read-only `/api/guest-booking/availability` fetch as `/book`: actual connected Inventory nightly tariffs, current stock, configured tax and saved bed limit. All hardcoded room/rate/stock/tax/limit fixtures have been removed. Lookup emails and reservation/payment creation remain disabled in preview. Missing database bindings, broken mappings, rates or settings produce unavailable/error states, never fabricated prices. A standalone `next start` without a working Cloudflare database context may therefore show unavailable; this code does not provision bindings, copy production data or proxy to production. Keep the local preview flag off in production.

## Confirmation email requirement (next booking-creation phase)

Confirmation email is sent best-effort after server-authoritative fulfilment (or accepted pay-at-property). A durable outbox with independent retries is still a follow-up; mail failure must never create a duplicate booking or charge.
