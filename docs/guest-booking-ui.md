# Guest booking browsing and private lookup

## Scope and rollout

The homepage hero and `/book` now contain the same **Find a stay / My booking** panel. This phase completes advisory browsing and a stay-review UI, not reservation creation. Public payment remains blocked; no gateway SDK, order, hold, PMS booking, receipt or confirmation is created by this panel. Existing Book Now eligibility and configured-provider routing remain intact.

Implementation order: (1) visible hero forms, (2) existing PMS online inventory and native hold exclusion, (3) complete server tariffs and restriction checks, (4) quantity/plan selection and review, (5) email-protected existing-booking retrieval, (6) responsive and adversarial tests. Live deployment/configuration is a separate step.

## Search and selection workflow

1. Choose check-in, check-out and 1–4 adult guests only. Beds are selected after Check availability, not in search. The strict query no longer accepts `units`. No children; Goko's 18–35 rule is prominently displayed. Dates are real civil dates: arrival today through 365 days ahead in IST, checkout later, maximum 30 occupied nights.
2. GET `/api/guest-booking/availability` validates a strict query and rejects duplicate keys. It is cloud-only, read-only and `no-store`.
3. Existing PMS range-picker allocations, blocks and OTA reservations determine online availability. The server uses nondeleted physical beds/dorms and excludes any overlapping unexpired `held` native inventory holds, using database time. Double beds require both physical slots. An absent internal holds table is permitted for advisory browsing because public hold creation is still disabled; an existing broken table or invalid hold data fails the search rather than being ignored.
4. Room cards group by dorm and sellable-unit type. No physical bed IDs, guest names, contact details, API credentials or owner tokens are returned.
5. Prices come from active existing Channel Manager room/rate-plan mappings and daily rates. Exactly one active room mapping per dorm is required. Each occupied night must have a positive safe whole-rupee rate; a departure-day row is also required to evaluate departure restrictions. Occupancy prices use adult1/adult2 when configured, otherwise the unit base rate. A mixed bunk/double dorm requires explicit adult2 prices for doubles; it cannot guess the single-bed tariff. Stop-sell, minimum/maximum stay, closed arrival/departure and advance-booking bounds are checked. Each eligible active rate plan is offered independently, not arbitrarily selected as the cheapest.
6. Cards show nightly breakdown and entire-stay price **per unit before taxes**. The selection/review summary adds estimated tax from the existing `booking_tax_rate` PMS setting, rounds once to whole rupees using the shared calculator, honors explicit 0%, and uses the existing 5% default only when the setting is absent. Corrupt/out-of-range saved tax fails search rather than guessing. These are estimates, not immutable accepted quotes. Missing/ambiguous/ineligible tariffs show an explanation and disable quantity selection; zero prices and fabricated rate fallbacks are not advertised.
7. Photo-led listings appear only after Check availability. Each eligible plan has a visible stay-price row and Add action. One plan applies to each category's selected quantity; Switch rate reprices without adding beds. Plus/minus obey stock and party size, rechecking current selection on every tap. Add stops when capacity covers guests; a whole double may provide excess capacity and is charged in full. Review requires sufficient capacity. Changing dates/party clears results; changing plan/quantity closes review. Photos reuse the marketing catalog by recognized luxury/female/mixed category name and are explicitly representative; unknown categories display a photos-coming-soon placeholder. No fabricated discounts, breakfast or instant-confirmation claims.
8. Review shows dates, party, selected units/plans, estimated subtotal, tax and total. Optional guest details remain only in component memory, are not persisted or sent to WhatsApp. No reservation or hold is created. Native date input/change events immediately invalidate previous results. Availability and lookup requests time out after 15 seconds and never automatically retry email/reservation/payment operations.
9. **Payment unavailable** is visibly disabled. A separate WhatsApp enquiry carries only dates, party and unit selection; the team must verify final availability, restrictions and the tax-inclusive price. Merely viewing or clicking Review never sends email or charges money.

## Mobile-first interface

The shared hero panel is designed for Goko's predominantly mobile guests. Fields and primary actions are at least 48px tall, with 16px input text, native date controls and appropriate email/phone/OTP keyboards and autocomplete. Dates sit side-by-side from 360px upwards but use full rows on narrower screens; Guests and Search span the phone width. Tabs occupy equal widths. Photo-led listings stack on phones with swipeable images and visible rate rows. At XL width the stay-summary sidebar sits beside the listings.

The compact summary uses CSS sticky positioning with gesture-area clearance on phones and top clearance in the XL sidebar, not a permanent fixed overlay. It shows selected beds/capacity and estimated tax-inclusive total, or Choose beds before selection. Dates/guests remain in the form/results heading and are repeated in the desktop sidebar; redundant dates/payment footer are omitted from the mobile summary to keep it compact. Payment remains explicitly blocked in the page/review. Hero clipping avoids creating a scroll container that breaks sticky positioning. Review moves focus and scrolls below the header. Float controls are hidden only on mobile while the booking panel intersects the viewport, restoring outside it; inline help remains. Booking, privacy, email, payment and permission contracts remain unchanged.

Homepage duplicate hero CTA buttons are hidden on phones (header Book remains available); desktop CTAs are unchanged. Booking hero headings/spacing are reduced on phones to bring search closer to the first screen. Mobile tests include source-level layout contracts plus browser checks; viewport emulation is not a substitute for physical iPhone/Android keyboard/date-picker testing before release.

Homepage room/closing copy no longer promises instant partner confirmation regardless of configured booking mode. This styling phase uses the existing component, browser controls and CSS; no picker/UI dependency, payment activation or booking-state mutation was added.

## Private existing-booking workflow

1. My booking takes a confirmation reference plus the booking email. POST `/api/guest-booking/lookup` action `request` searches nondeleted PMS bookings by Goko/external reference and email, case-insensitively. Missing and duplicate matches disclose nothing.
2. Every request returns a fresh opaque challenge ID and the same generic message. A matched booking atomically claims one code per booking/email per ten minutes, including across reference aliases. Throttled retries do not return the previous challenge ID (which would be an enumeration signal). Keep the original page open; repeated requests may return an unusable opaque challenge until the cooldown expires.
3. Six-digit cryptographic codes are emailed from **info@gokohostel.com**, through the existing Cloudflare `EMAIL` binding, to the stored booking address. Only a salted/secret-bound hash is stored. No plaintext code or contact address is stored in the challenge table. Ambiguous delivery retains the cooldown and produces a sanitized operational warning, not an existence-revealing guest error.
4. `verify` accepts only a UUID challenge and six digits, using POST bodies, never URL parameters/storage. The database atomically counts attempts (maximum five) and expiry; successful codes are consumed once. Concurrent verification can disclose details only to one successful request.
5. Details are a minimized current booking snapshot: reference, guest name, dates, room type, guest count, booking/payment status and INR total/paid/refunded. No contact data, raw OTA payload, identity documents, bed IDs or gateway identifiers are returned. This read-only view cannot authorize refunds, cancellation or payment.
6. Cross-origin browser requests are rejected; body streaming is limited to 4 KiB. Responses are sanitized, `no-store`, and `no-referrer`. Pi returns 403 before reading storage or sending email.

Activation requires migration **0061_guest_booking_lookup.sql**, an independently provisioned **GUEST_BOOKING_LOOKUP_SECRET** of at least 32 characters, and a working verified sender/EMAIL binding. Absence fails closed with a helpful contact option. Do not put the secret into a public environment variable, CMS or source control. No live migration or secret change is performed by this code change.

Before public lookup activation, configure edge/IP request limits and verify delivered messages, origin handling on the deployed canonical hostname, database races and expiry on deployed D1. The per-booking cooldown/attempt limit is not a replacement for edge abuse controls or a formal resistance-to-timing-enumeration review. Schedule expiry cleanup for this ephemeral table; do not sync it to Pi.

## Safe visual preview

For local UI review only, start with `GOKO_BOOKING_UI_PREVIEW=true` and visit `/book/preview`. Otherwise the route returns 404 and has noindex metadata. Sample dates/prices/availability are explicitly labelled. Results start hidden; Search shows the sample dataset and restores sample dates while retaining the selected guest count. No live availability queries, lookup email, reservations or payments occur. Never enable this flag on production or use fixture prices as tariffs.

## Confirmation email requirement (next booking-creation phase)

The existing enquiry acknowledgement and lookup code are **not booking confirmations**. After actual native fulfilment is implemented, a durable notification outbox must be inserted with the PMS booking commit, with one unique confirmation event per booking. Send from `info@gokohostel.com` only after server-authoritative payment verification and successful fulfilment (or an explicitly accepted pay-at-property booking). Include reference, guest, dates, units, tax-inclusive price, verified paid/balance amounts, policies and the private My booking instructions. Retry delivery independently of booking creation; never create a duplicate booking or charge due to a mail failure. Provider capture/browser success alone cannot trigger confirmation. That outbox/fulfilment trigger remains blocked together with public checkout in this phase.
